# 后续开发指导：P3 收口与 Phase 4 规则整理

> 更新日期：2026-10-13。本文是下一位开发者的执行说明，必须与
> `docs/DEVELOPMENT_GUIDE.md`、`docs/STATUS.md`、
> `docs/phase-4-development-guide.md` 一起阅读。

## 1. 当前基线

- Phase 0–2 已可用：本地索引、同步、导出、受控 `OperationPlan`、批准、审计与执行器均已存在。
- Phase 3 已提供可选网站权限、检查进度、暂停/继续/取消、HEAD/GET 复核和书签页状态标签。
- 链接状态不是“可用/失效”二分法：`redirect_pending`、`network_error`、`rate_limited`、`permission_required`、`unsupported` 与 `outdated` 都不得被当作失效。
- P3 仍有一个可靠性缺口：扫描队列、限流状态和取消状态只在内存中；MV3 Service Worker 重启后不能恢复。此项必须在引入任何新的长任务前解决。

## 2. 工作顺序与范围

### 里程碑 A：完成 P3 的可恢复任务底座（先做）

目标：让链接扫描在 Service Worker 重启、浏览器重开、暂停和限流后能安全继续，而不重复把旧结果写成新结果。

必须实现：

1. Dexie 增加 `scanJobs` 和 `scanItems`；保存运行状态、创建时间、基于的 `syncGeneration`、游标、每项尝试次数、下一次执行时间、取消标记和租约。
2. 用 `chrome.alarms` 唤醒到期任务；启动时回收过期租约并继续未完成项目。
3. 每个写入结果必须同时校验 bookmarkId、原始 URL 和 syncGeneration；书签已修改时把项目标为过期，不覆盖新书签的状态。
4. 暂停、继续、取消均需持久化。取消后不得重新领取或产生新的检查结果。
5. 扫描状态 API 返回 jobId、可恢复状态、已完成/等待/进行中/取消数、下次唤醒时间和最后错误；UI 只展示事实，不能假称“已完成”。

不做：自动删除书签、隐藏网络错误、自动跟随不可见重定向、伪造 DNS 验证。

最低验收：开始 20 条扫描后重载扩展或终止 Service Worker；重新打开页面后任务能继续，已完成项不重复执行，已改 URL 的书签不显示旧结果。

### 里程碑 B：Phase 4 — 规则整理与重复检测

目标：在不调用 AI、不自动修改原生书签的前提下，生成可解释、可忽略、可预览的整理建议。

实施顺序必须如下：

1. **数据模型与迁移**：新增 `organizationRuns`、`duplicateGroups`、`folderFindings`、`rules`、`suggestions`。所有分析结果保存 `syncGeneration`、稳定指纹、状态和生成理由。
2. **纯函数优先**：实现 `url-normalizer.ts`、`duplicate-detector.ts`、`folder-analyzer.ts`，不依赖 Chrome、Dexie 或 UI。
3. **组织分析服务**：按当前同步版本创建一次分析 run；支持状态、取消和过期判定。重复检测只能按规范化键分组，禁止 O(n²) 两两比较。
4. **规则与建议生命周期**：规则只支持域名、URL 前缀、标题关键词、当前目录、重复类型；排序为“优先级降序、规则 ID 升序”。冲突必须保留，不能静默选一个目标。
5. **UI 与计划预览**：新增“智能整理”页，含概览、重复组、目录问题、规则、建议。建议可以忽略/恢复忽略/筛选/选择；点击“生成计划草案”仅创建 `OperationPlan`，不得直接调用 `chrome.bookmarks`。

## 3. URL 比较规范

只允许用于比较，绝不改写书签原始 URL：

- 允许：协议/hostname 大小写标准化、移除默认端口、移除明确跟踪参数（`utm_*`、`gclid`、`fbclid`）。
- 保留：路径大小写、普通 query、非空 fragment、不同子域名、HTTP 与 HTTPS、www 与非 www。
- `token`、`signature`、`expires`、`session` 等敏感/时效参数出现时，结果只能标为“需人工确认”，不得生成自动合并或删除建议。
- 同目录完全重复可提出候选处理建议；跨目录重复只标记原因，默认不建议删除。

## 4. 目录与建议规则

P4 首版可识别：空目录、单书签目录、过深目录、书签过多目录、同父级同名目录、完全重复、规范化重复和跨目录重复。

系统根目录、书签栏、其他书签、移动端目录不得生成删除建议。目录语义合并、主题判断和内容相似度不属于 P4，留给后续 AI/正文阶段。

每条建议必须有：稳定指纹、来源、受影响对象、理由、风险等级、置信度、状态、生成时间、syncGeneration。忽略状态按稳定指纹保存；重新运行分析不得让用户已忽略的同一建议重新出现。

## 5. 安全与停止条件

- 未经用户批准，绝不删除、移动、重命名、合并原生书签。
- P4 不能读取网页正文、不能调用 AI、不能扩大网站权限。
- 不得把 `confirmed_dead` 当作删除理由；链接检查只是一项展示证据。
- 数据库迁移、计划草案到执行器的字段映射、或任何批量写入路径不确定时，停止并反馈。
- 开发中发现 Worker 恢复会重复执行任务、建议会跨 generation 误复用、或规则冲突会静默覆盖时，停止并先修复。

## 6. 验证与交付

以完整功能可运行和人工验收为主，不要求高覆盖率或压力基准。每个里程碑至少运行：

```powershell
npm run typecheck
npm run lint
npm run test
npm run build
```

为新增的核心纯函数、结果过期、忽略状态保持、规则冲突、以及“建议只能生成草案、未批准不写书签”补充必要回归测试。

交付报告必须写明：改动文件、迁移版本、实际命令结果、浏览器手工验证项、未验证项、权限/隐私变化、已知限制和下一步阻塞项。没有真实浏览器验证时，不得写“完整验收通过”。

## 7. 可直接交给开发 Agent 的任务说明

> 先完成 P3 可恢复扫描任务底座，再实施 Phase 4 的默认只读整理分析。严格遵守 `docs/NEXT_DEVELOPMENT_GUIDE.md`。先检查现有 Dexie schema、消息协议、OperationPlan 和同步 generation；新增分析或扫描结果必须绑定 bookmarkId、原始 URL 与 syncGeneration。P4 只生成可解释的重复组、目录问题和建议，绝不直接写入 `chrome.bookmarks`。所有用户可执行操作只能创建计划草案，并继续使用已有批准和执行器。完成后运行 typecheck、lint、test、build，记录真实结果与浏览器手工验证缺口，然后停止等待人工验收。
